# Projects

Projects are the integration mechanism for the roadmap. They turn individual techniques into
reviewable systems and expose gaps that topic-by-topic exercises often hide.

## Project progression

| Tier | Scaffolding | Primary purpose |
| --- | --- | --- |
| Guided | Architecture and acceptance criteria are supplied | Learn a complete delivery loop with feedback. |
| Specification-led | Requirements and constraints are supplied | Practice technical choices and trade-off documentation. |
| Capstone | The learner owns problem framing through operations | Demonstrate independent AI engineering judgment. |

Projects should be distributed across the learning path. The root [roadmap](../ROADMAP.md) defines
gates after engineering foundations, applied ML, deep learning, LLM engineering, and production
operations.

## Required project evidence

- A user-centered problem statement, measurable acceptance criteria, and explicit non-goals.
- Reproducible setup, versioned dependencies, safe configuration, and automated tests.
- A baseline, representative evaluation data, chosen metrics, and failure analysis.
- Architecture decisions with alternatives and consequences.
- Operational evidence covering telemetry, failure handling, security, privacy, and cost.
- A concise demonstration, runbook, retrospective, and limitations statement.

## Review dimensions

Projects are reviewed on product fit, implementation quality, evaluation validity, reliability,
security and safety, cost awareness, and communication. Complexity is not a scoring category. A
smaller system with strong evidence is preferable to a broad system whose behavior cannot be
verified.

## Capstone standard

An independent reviewer should be able to reproduce the main result and trace important claims to
code, data, configuration, or measurements. Manual demo-only steps, undisclosed data preparation,
and unbounded model or tool behavior are material defects.
